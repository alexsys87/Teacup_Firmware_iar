## Тесты Renode в Windows (автоматическая настройка)

Откройте командную строку в **папке `test`** загруженного репозитория и выполните:

```bat
run-renode.cmd
```

Лицензия IAR, права администратора, глобально установленный Python и изменения
PATH не нужны. В 64-разрядной Windows 10/11 скрипт запуска скачивает и кэширует
переносимые Renode 1.17.0, Python 3.12.10, Arm GNU Toolchain 14.3.rel1 и xPack
Windows build tools 4.4.1-3 (make, BusyBox sh, mkdir и rm). Для первого запуска
нужны доступ к интернету и несколько ГБ свободного места; последующие запуски
используют уже скачанные инструменты. Кэш расположен в
`%LOCALAPPDATA%\Teacup_Firmware\renode-tools`. Для архивов Renode, Python и xPack
проверяются зафиксированные SHA-256; версия Arm зафиксирована, загрузка выполняется
по HTTPS. Эти инструменты нужны для тестов, а не для работы прошивки.

По умолчанию **Baseline** пересобирает прошивку с `TEST=1` для **F401 и F411**,
запускает `run_tests.py all` через **UART и USB CDC**, а также по одному запуску
`run_usb.py` для каждого чипа: проверяются USB-дескрипторы, маршрутизация между
одновременно работающими портами, аварийные команды, сброс, управление потоком,
запросы к конечным точкам и отключение/повторное подключение. Итого — шесть запусков
наборов тестов. Существующие проверки поведения прошивки не изменены. Это проверки
в эмуляторе, а не замена проверки электрических характеристик на реальной плате.

```bat
rem Только один чип; UART, USB и проверка совместной работы портов остаются
run-renode.cmd -Chip F411

rem Сокращённый baseline (проверка совместной работы USB-портов остаётся)
run-renode.cmd -Chip F401 -Port uart -Part basic,proto

rem Рабочая конфигурация P3 Steel: TEST=0, на F401
run-renode.cmd -Suite P3Steel -Chip F401

rem Пересборки для отдельных функций: BLTouch, MPC, PT100, экструдеры, лазер
run-renode.cmd -Suite Features -Chip F401

rem Все переносимые в Windows наборы: baseline на обоих чипах, остальные на F401
run-renode.cmd -Suite All

rem Показать точные наборы тестов и параметры сборки после подготовки инструментов
run-renode.cmd -Suite All -List

rem Скачать/проверить инструменты без сборки либо выполнить самопроверки запуска
run-renode.cmd -PrepareOnly
run-renode.cmd -SelfTest

rem Изменить каталог кэша или лимит времени для каждой сборки/каждого теста
run-renode.cmd -ToolsDirectory "D:\Portable Tools\Teacup" -TimeoutSeconds 3600
```

В PowerShell используйте `./run-renode.cmd` с теми же аргументами. При запуске
из корня репозитория добавьте перед командой `test\`. Обёртка `.cmd` запускает
Windows PowerShell 5.1 с обходом политики выполнения только для этого процесса;
системная политика не меняется. Пути с пробелами поддерживаются и отдельно
проверяются в Windows CI.

**Расширенное покрытие:** `P3Steel` включает дуги, калибровку, input shaping,
linear advance, lookahead, дополнительные функции движения, интеграцию P3 Steel,
мощность нагревателей, восстановление после потери питания, профилирование,
качество печати, скорость и SPI flash. `Features` включает два экструдера,
BLTouch/mesh/runout/babystepping, индуктивный датчик, лазер, шпиндель, MPC,
MAX31865/PT100, TMC UART и выравнивание Z-моторов. Точные параметры сборки находятся
в `test/renode/windows-suites.json`. Каждый запуск принудительно выполняет свежую
сборку (`make -B`); внутри одного запуска повторно используются только образы
с одинаковыми значениями chip, TEST и EXTRA. Разные конфигурации имеют отдельные
каталоги сборки. Расширенные наборы выполняются **только на F401**, поскольку
несколько исходных скриптов содержат платформы F401 и привязанные к ним временные
допущения. Выбор только F411 с `P3Steel` или `Features` считается ошибкой, а не
успешным пропуском тестов.

**Ограничения `-Suite All`:** это все 23 переносимых в Windows пакетных скрипта
(скрипт лазера запускается дважды), а не каждый скрипт репозитория. `run_menu.py`
(OLED/LCD) и `run_sdcard.py` по-прежнему требуют Linux-инструменты `mkfs.fat`/mtools,
а `run_printcore.py` — Printrun и pyserial. Для этих трёх скриптов не заявляется
покрытие или автоматическая установка зависимостей. Следуя исходному набору,
`all` в baseline намеренно не включает медленную автонастройку PID и завершающую
работу DFU. При необходимости запускайте их явно через `-Part tune` или
`-Part dfu`. Расширенные наборы могут выполняться несколько часов и требовать
значительного объёма RAM; они запускаются последовательно, не параллельно.

Журналы, monitor-скрипты и машиночитаемый `summary.json` сохраняются в
`test/results/<chip>-<suite>/`; журнал верхнего уровня `launcher.log` фиксирует
запуск. Коды завершения: **0** — успех, **1** — ошибка сборки прошивки или теста,
**2** — ошибка загрузки/настройки инструментов, **124** — превышение лимита времени.
При тайм-ауте завершается дерево дочерних процессов Windows и сохраняются журналы;
успех не сообщается. Неудачную загрузку/распаковку можно повторить; при необходимости
удалите каталог соответствующего инструмента из кэша.

Workflow `Renode Windows tests` автоматически подготавливает инструменты,
запускает реальные baseline-тесты по умолчанию на обоих чипах (UART и USB),
а также самопроверки скрипта запуска. Переносимые инструменты кэшируются,
а `test/results` загружается как артефакт даже при ошибке задания.

## Проверка (необязательно, Linux)

```
cd test/gcc
make CHIP=F401 TEST=1     # сборка gcc с тестовой конфигурацией
cd ../renode
./run_tests.py /path/to/renode ../gcc/build_F401_1/teacup.elf stm32f401.repl
```

Тесты проверяют:

- запуск;
- M115, M105, M119;
- число шаговых импульсов и скорость движения;
- очередь с lookahead;
- ожидание нагрева (M104/M116);
- хоуминг по концевику;
- ШИМ нагревателя (M106);
- отсутствие сброса по watchdog.

Сборку с таймерными импульсами тесты распознают по сообщению при старте
и считают шаги по записям в регистр `CR1` таймеров вместо записей в
`BSRR`:

```
make CHIP=F401 TEST=1 EXTRA="-DSTEP_TIMER_PULSES -DSTEP_CODE_IN_RAM" BUILD_SUFFIX=_stim
```

`run_spiflash.py` проверяет SPI flash на конфигурации P3 Steel с моделью
W25Q64 (`models/TeacupW25Q.cs`, платформа `stm32f401_dma_flash.repl` /
`stm32f411_dma_flash.repl`). Проверяются:

- определение микросхемы;
- `M500` во время движения;
- загрузка настроек после сброса;
- загрузка файла через `M28`/`M29` (больше одного сектора);
- `M20`, `M23`/`M24`/`M27`, печать до конца;
- `M30`, `M9002`.

`test/pff/run.sh` — тест порта Petit FatFs на ПК. Нужны `mkfs.fat` и
`mcopy` (пакеты dosfstools, mtools). Тест создаёт образы FAT16 и FAT32 и
проверяет:

- чтение файла из 6000 строк через `pf_parse_line()`;
- список файлов в каталоге;
- `pf_lseek()` в середину файла;
- CR LF, пустые строки, последнюю строку без перевода строки и то, что
  остаток последнего сектора (строки удалённого файла) не читается.

`run_sdcard.py` проверяет SD-карту на шине SPI flash. На SPI1 висят
три модели — W25Q64 (CS PA4), SD-карта (`models/TeacupSDCard.cs`, CS PC14)
и MAX31865 (CS PC15) — через модель шины (`models/TeacupSPIMux.cs`). Она
считает байты, переданные при нескольких выбранных устройствах. Образ
карты — FAT32 с таблицей разделов, как на бывшей в употреблении карте:
файл фрагментирован и кончается в кластерах удалённого файла, в остатке
последнего сектора лежат строки `M112`. Нужны `mkfs.fat` и mtools.
Проверяются:

- монтирование при старте, `M20` (размеры, подкаталог, длинное имя,
  без скрытых и удалённых файлов), сообщения `M23`;
- печать с карты, в файле `G4`, `M105`, `M500` (запись в flash во время
  чтения файла);
- пропадание питания в середине и `M1000`: запись в flash называет файл
  на карте, печать продолжается до конца;
- последняя строка без перевода строки выполняется, после конца файла
  ничего не читается;
- ни одного конфликта на шине;
- без карты — `SD init fail`, после вставки `M21` монтирует;
- медленная карта (ACMD41 ~1 с): монтируется без сброса watchdog.

```
make CHIP=F401 TEST=0 EXTRA="-DSD_CARD_SELECT_PIN=PC_14 -DHOTEND_MAX31865" BUILD_SUFFIX=_sd
./run_sdcard.py <renode> ../gcc/build_F401_0_sd/teacup.elf stm32f401_dma.repl
```

Часть `perf` проверяет оптимизации шагового прерывания:

- `M9001` — каждый шаг получает конец импульса;
- после движения все STEP-пины в нуле;
- после срабатывания концевика ось проходит только путь торможения:
  39 шагов против 50 без прерываний EXTI.

Часть `slicer` отправляет 49 строк G-кода в том виде, как их
генерирует PrusaSlicer, с номерами строк и контрольными суммами, как это
делает Pronterface. Одна строка специально испорчена. Тест проверяет:

- пересылку испорченной строки;
- что на каждую строку приходит ровно одно `ok`;
- что неизвестные команды не ломают печать;
- что `M84 X Y E` не двигает оси;
- конечную позицию.

**USB.** В Renode 1.16 нет модели OTG_FS, поэтому она своя:
`models/TeacupSTM32_OTGFS.cs`. Модель описывает регистры ядра в режиме
устройства на уровне транзакций: очередь RX FIFO со статусами, TX FIFO
для каждой конечной точки, EPENA/NAK/STALL, счётчики пакетов, проверку
адреса. Прерывания STUP и XFRC возникают после чтения статуса из
очереди, как в настоящем ядре. Нарушения протокола со стороны прошивки
(переполнение FIFO, чтение без данных, лишние байты в статусной стадии и
т. п.) попадают в лог как `usb: PROTOCOL …`.

Встроенный хост перечисляет устройство так же, как Linux: сброс шины,
дескрипторы, `SET_ADDRESS`, строки, `SET_CONFIGURATION`, открытие порта
(`SET_CONTROL_LINE_STATE`, line coding). Затем он работает как терминал:
для Renode модель — это UART, поэтому `WriteChar`, `LoggingUartAnalyzer`
и сокет-терминалы работают как с USART. Команды монитора для тестов:
`Open`/`Close` (DTR), `Plug`/`Unplug`, `HostReads true|false`,
`Control "имя" "setup hex" длина`, `Stats`.

Все части `run_tests.py` можно прогнать через USB:

```
TEACUP_PORT=usb ./run_tests.py <renode> ../gcc/build_F401_1/teacup.elf stm32f401_dma.repl all
```

Сообщения при загрузке (`start`) при этом проверяются в UART.

`run_usb.py` проверяет USB отдельно (сборка `make CHIP=F401 TEST=1`):

- перечисление: дескрипторы, строки, серийный номер из UID, STALL на
  device qualifier и на неизвестные запросы, line coding;
- ответы только в порт, откуда пришла команда; свои номера строк у
  каждого порта; `Resend` только в свой порт;
- `M108` по USB отменяет `M109` из UART; `M112` по USB сообщается в оба
  порта; `M999` по USB в остановленном состоянии; перечисление заново
  после сброса;
- 80 строк одним блоком: хост получает NAK, ни одна строка не теряется;
- хост не читает, порт закрыт, кабель вынут и вставлен: принтер и UART
  работают, сброса по watchdog нет;
- остановка конечной точки (`SET_FEATURE`/`CLEAR_FEATURE` ENDPOINT_HALT).

```
./run_usb.py <renode> ../gcc/build_F401_1/teacup.elf stm32f401_dma.repl
```

Модель повторяет описание ядра из RM0368 и поведение, известное по
другим драйверам DWC2, но это не кремний: проверку на настоящей плате
под Windows и Linux она не заменяет.

`run_power.py` проверяет управление блоком питания и проверку
выключенного нагревателя на конфигурации P3 Steel (сборка
`make CHIP=F401 TEST=0`, температуры подставляются в буфер АЦП):

- PB2 после старта в низком уровне; `M80`, `M81`; нагрев сам включает
  блок; после 35 с простоя блок остаётся включённым;
- выбег +8 °C после выключения хотэнда и медленный рост 0,33 °C/с (сопло
  на горячем столе) не вызывают останова;
- рост 3 °C/с при выключенном хотэнде останавливает принтер
  (`Heater_ID: 0`), PB2 уходит в низкий уровень, ШИМ принудительно
  выключен; после `M999` блок остаётся выключенным;
- стол растёт на 0,5 °C/с при выключенном нагреве: останов с
  `Heater_ID: bed`.

```
./run_power.py <renode> ../gcc/build_F401_0/teacup.elf stm32f401_dma.repl [all|supply|hotend|bed]
```

`run_speed.py` проверяет, что скорость не зависит от направления. На
сборке P3 Steel делается 14 движений по 150 мм на 50 мм/с в разных
направлениях, два из них с небольшим Z. Разброс времени должен быть
меньше 1 %: сейчас разницы нет в пределах разрешения лога (10 мс). С
ускорением по самой быстрой оси было 0,33 % (диагональ разгонялась
быстрее), до точного квадратного корня в разгоне 0,66 %, со старым
приближением длины 23 %.

`run_profile.py` — статистический профилировщик: каждые ~200 мкс
считывает адрес выполняемой инструкции и показывает долю CPU по частям
прошивки для нескольких типичных нагрузок. `PROFILE_LOG=<лог>`
повторно разбирает лог прошлого прогона.

`run_lookahead.py` проверяет lookahead на сборке P3 Steel. Хук на
`dda_start()` пишет виртуальное время начала каждого движения, отсюда
средняя скорость каждого отрезка. Два сценария на 100 мм/с: окружность
`G2` радиусом 5 мм (отрезки 0,63 мм) и многоугольник из 120 отрезков `G1`
по 0,35 мм, которые приходят по одному, как от хоста на 115200 бод:

- общее время близко к «разгон — крейсер — торможение»;
- крейсерская скорость достигается и не превышается, провалов между
  отрезками нет;
- ускорение между отрезками не выше заданного (вдоль пути, без √2 на
  диагоналях);
- `M114` равен конечной точке; в очереди движений 63 свободных места.

Ещё два сценария проверяют ускорения:

- ретракт 3 мм на 25 мм/с идёт с ускорением `M204 R` (5000 мм/с²);
- 20 мм по диагонали 45° занимают столько же времени, сколько 20 мм
  вдоль X.

```
./run_lookahead.py <renode> ../gcc/build_F401_0/teacup.elf stm32f401_dma.repl
```

`run_linear_advance.py` проверяет linear advance на сборке P3 Steel.
Хук на `dda_start()` записывает номинальную позицию E и позицию мотора,
шаги E считаются по запускам TIM3 с направлением по PB5:

- K = 0: опережения нет, шагов назад нет;
- K = 0,05: опережение на крейсерской скорости равно K × скорость подачи,
  при торможении экструдер шагает назад;
- шагов вперёд минус шагов назад ровно столько, сколько номинальных шагов;
  после движений мотор стоит в номинальной позиции;
- ретракт и подача (только E) идут без опережения;
- `M900 K`, отчёт в `M503`, сохранение `M500`/`M501`, отказ при K > 10.

```
./run_linear_advance.py <renode> ../gcc/build_F401_0/teacup.elf stm32f401_dma.repl
```

`run_input_shaping.py` проверяет input shaping и S-кривую на сборке P3
Steel. Хуки на `shaper_step()` (шаги Брезенхема с точным временем
таймера) и `shaper_pulse()` (импульсы мотора с направлением по PA9/PA10)
дают номинальные и реальные шаги. По ним тест считает формированную
позицию (Σ A·x(t − T), усреднённую по окну S) и сравнивает её с позицией
мотора на каждом импульсе:

- без `M593` шаги X/Y идут мимо формирователя;
- `M593 F` не меняет скорость следующих движений;
- ZV/MZV без S-кривой и с ней: позиция мотора совпадает с формированной
  позицией с точностью до шага; шагов вперёд минус назад ровно столько,
  сколько номинальных; `M114` верный; переполнений истории нет;
- средняя задержка мотора равна Σ A·T + S/2;
- отчёт `M593`, сохранение `M500`/`M501`, отказ при неверных `T` и `D`.

```
./run_input_shaping.py <renode> ../gcc/build_F401_0/teacup.elf stm32f401_dma.repl
```

`run_motion_extras.py` проверяет на сборке P3 Steel перекос XY (`M852`),
люфт X, Y, Z со сглаживанием (`M425`), прошивочный ретракт (`G10`/`G11`, `M207`/`M208`),
реакцию на потерю хоста (`M86`) и сохранение всего этого:

```
./run_motion_extras.py <renode> ../gcc/build_F401_0/teacup.elf stm32f401_dma.repl
```

`run_laser.py`, `run_extruders.py`, `run_tmc.py`, `run_quality.py`,
`run_calibration.py` и `run_mpc.py` проверяют:

- лазер и шпиндель;

Модель механики (`models/p3_model.py`) работает в Python внутри Renode,
через хуки на запись в выходы шагов: считает положение сопла по шагам
X/Y/E (запуски TIM1–TIM3) и Z (PB12) с учётом DIR, замыкает концевики
X/Y, понимает команды серво (TIM9 CCR1) и поднимает сигнал зонда на
PB15, когда кончик щупа касается стола. Стол наклонный и с горбом,
билинейным в ячейках сетки 3×3. Поэтому сопло держит постоянный зазор
над ним, только если движения режутся на границах ячеек. Чтобы хуков
было меньше, шаги/мм уменьшены через `M92`. Проверяется:

- `G28`: X/Y по концевикам, Z зондом в центре стола, 2 замера,
  выдвигание и уборка щупа, импульсы на PC13;
- `G30` и 9 узлов `G29` против формы стола (±8 мкм);
- зазор 0,2 мм на всей диагонали через горб, логический Z не меняется;
- `M290`: сразу, в следующем движении и во время движения; `M114` не
  меняется;
- высота затухания, `M420 S0`/`S1` без движения моторов;
- `M500` → `M502` → `M501` для сетки, `M851`, `M412`;
- окончание филамента во время «печати»: пауза после буферизованных
  движений, парковка, ретракт + выгрузка, `busy: paused for user`,
  продолжение по `M108`; координаты и E после продолжения те же, баланс
  филамента сходится;
- `M600` с продолжением по `M876 S0`, `M412 S0`, `M119`.

Во всех тестах на сборке P3 вход PA0 держится в 1, как подтяжка на
плате: в Renode вход по умолчанию 0, то есть «нет филамента».

### Оптимизации шагового прерывания

**Проверка:** сборки с `-DMULTISTEPPING -DMULTISTEP_MIN_CYCLES=5000`
(мультишаг уже от 17 кГц) проходят `run_tests.py all` и `run_arcs.py`, а
`run_lookahead.py` и `run_linear_advance.py` — с квантом Renode 1 мкс
(`emulation SetGlobalQuantum "0.000001"`): число шагов, позиции,

Renode пропускает сравнение CC4, поставленное чуть впереди счётчика, и
генератор E (linear advance) отстаёт — на STM32 такого нет.

### UART через DMA

**Модели для тестов.** Штатные модели Renode 1.16 не умеют запросы DMA от
UART, флаг IDLE и циклический режим DMA. Поэтому тесты используют
собственные модели из `test/renode/models/`, которые Renode компилирует
при запуске:

- `TeacupSTM32DMA.cs` — копия модели Renode с добавленным циклическим
  режимом (CIRC);
- `TeacupSTM32_UART.cs` — минимальная модель USART с запросами DMA и
  флагом IDLE.

- `TeacupSTM32_OTGFS.cs` — ядро OTG_FS (DWC2) в режиме устройства вместе
  с USB-хостом, см. ниже.

Платформы с этими моделями: `stm32f401_dma.repl`, `stm32f411_dma.repl`.
Сборку с `NO_SERIAL_DMA` проверяйте на `stm32f401.repl` /
`stm32f411.repl` со штатными моделями.

### Восстановление после пропадания питания (`POWER_LOSS_RECOVERY`, `M413`, `M1000`)

**Проверка** (`run_power_loss.py`, сборка P3 Steel, модель W25Q64 и
модель механики): файл из 6 слоёв, перезапуск посреди печати (`M112`,
`M999`: ОЗУ теряется, SPI flash и механика остаются). После перезапуска
сообщается Z выполнявшейся строки (совпадает с физическим Z), `M1000`
допечатывает файл до конца, конечная позиция верная, подано всё
филамента файла плюс повтор начатого слоя (не больше одного слоя); после
законченной печати записи нет.

### Lookahead по всей очереди

**Проверка** (`run_lookahead.py`, сборка P3 Steel, 100 мм/с):

| Сценарий | Было (стыковка двух движений) | Стало |
|---|---|---|
| `G2` r 5 мм, 50 отрезков по 0,63 мм | 37–45 мм/с «пилой», 0,877 с | 100 мм/с, 0,458 с |
| 120 отрезков `G1` по 0,35 мм | 27–33 мм/с, 1,509 с | 97–100 мм/с, 0,556 с |

Идеал («разгон — крейсер — торможение» за один раз) — 0,414 с и 0,520 с.
Цифры «стало» — с ускорением вдоль пути: диагональные отрезки больше не
разгоняются в √2 раз сильнее заданного.
Остаток — первое движение с остановкой и стыки, ограниченные рывком: у
многоугольника это 97–98 % скорости на стыках около 45°. Старой прошивке
отрезки `G1` подавались раз в 11 мс: при 16 местах в очереди поток на
115200 бод переполнял буферы.

### Linear advance (`LINEAR_ADVANCE`, `M900 K`)

**Проверка** (`run_linear_advance.py`, сборка P3 Steel): многоугольник из
60 отрезков по 0,35 мм с E на 100 мм/с (0,035 мм филамента на мм пути):

| | K = 0 | K = 0,05 |
|---|---|---|
| Опережение на 100 мм/с | 0 | 284,6 шага = 0,17 мм (K × скорость подачи: 292,6) |
| Шагов E вперёд / назад | 1204 / 0 | 1474 / 270 |
| Мотор E после движений | в номинальной позиции | в номинальной позиции |

Опережение чуть меньше расчётного, потому что крейсерская скорость
многоугольника 97–100 мм/с. Номинальных шагов E в обоих случаях 1204.

### Input shaping и S-кривая (`INPUT_SHAPING`, `M593`)

**Проверка** (`run_input_shaping.py`, сборка P3 Steel): X — ZV 40 Гц, Y —

|---|---|---|
| X, ZV 40 Гц | 0,50 шага | 5,30 / 5,30 мс |
| Y, MZV 30 Гц | 0,82 шага | — / 10,83 мс |
| X, ZV 40 Гц + S 10 мс | 0,50 шага | 10,31 / 10,30 мс |

### IAR: оптимизация

**Замеры в Renode** (F401, 800 шагов, `M9001`). Renode считает
инструкции, а не реальные такты, поэтому это грубая оценка:

| Сборка (GCC) | Такты прерывания (сред.) | Flash |
|--------------|--------------------------|-------|
| `-Os` везде | 103 | 28 160 Б |
| `-Os` + `-O2` для файлов движения | 105 | 28 924 Б |
| `-O2` везде | 105 | 32 452 Б |
| `-Os` + `-O2` + LTO (межфайловое встраивание) | **87** | 29 152 Б |

Вывод: переключение `-Os`/`-O2` по числу инструкций почти ничего не
меняет. Выигрыш около 17 % даёт встраивание функций между файлами:
прерывание → `queue_step()` → `dda_step()` без вызовов. В IAR это
Multi-file compilation. Реальный эффект на плате (задержки Flash, кэш ART)
проверяйте командой `M9001`.

### Планировщик на FPU: профилирование

**Нагрузка на CPU** (`run_profile.py`, доля выполненных инструкций в
Renode, сборка P3 Steel):

| Нагрузка | Простой | Шаговое прерывание |
|---|---|---|
| 360 отрезков G1 по 0,35 мм на 60 мм/с | 98 % | 0,7 % |
| G1 на 150 мм/с (24 кГц) | 97 % | 2,8 % |
| ретракт 25 мм/с (41,8 кГц) | 95,5 % | 4,5 % |

На реальной плате с учётом входа в прерывания и промахов кэша это
примерно 5–11 % CPU на пиковых частотах шагов. CMSIS-DSP в прошивке
применить некуда: в ней нет фильтров, БПФ и матриц.

## Совместимость моделей с Renode 1.17.0

Во всех шести описаниях платформ F401/F411 (обычное, DMA и DMA+flash)
I2C использует тип `I2C.STM32F1_I2C`. Именно этот тип применяется к STM32F4
в [исходной платформе Renode v1.17.0](https://github.com/renode/renode/blob/v1.17.0/platforms/cpus/stm32f4.repl).
Прежнее имя `I2C.STM32F4_I2C` отсутствует в переносимой версии и вызывало
`Error E04: Could not resolve type` ещё до выполнения прошивки. Изменено
только имя типа: адреса I2C, подключения `EventInterrupt`/`ErrorInterrupt`,
прошивка и её проверки сохранены. Это совместимость описания платформы,
а не подтверждение работы аппаратного I2C или ослабление тестов.

Путь запуска `.resc` явно заключён в кавычки на уровне монитора Renode,
поэтому поддерживаются папки с пробелами. Стандартный ввод остаётся
открытым до завершения эмуляции. Лаунчер также следит за конкретными
ошибками загрузки/разбора монитора и останавливает процесс, не ожидая
30 минут интерактивного приглашения. Обычный ответ прошивки `Error:`
(например, срабатывание температурной защиты) не считается такой ошибкой.
Генератор случайных чисел также использует точное определение из upstream
STM32F4 для Renode 1.17.0: `Miscellaneous.STM32_RNG` с `series: STM32Series.F4`.
Несуществовавшее имя `Miscellaneous.STM32F4_RNG` заменено без изменения адреса
`0x50060800` и линии прерывания `nvic@80`.
Для `SPI.STM32SPI` добавлен обязательный параметр `series: STM32Series.F4`
из той же upstream-платформы; опечатка имени выхода `DMARecieve` исправлена
на поддерживаемое `DMAReceive`. Адреса SPI и существующие номера подключений
не изменены. Это устраняет ошибку конструктора `E25` до запуска прошивки.

## Проверки Teacup Host

Требуется .NET 8 SDK. Команды выполняются из корня репозитория:

Тесты ядра (разбор G-кода, построение траектории, протокол с виртуальным
принтером: Resend, загрузка `M28`/`M29`, печать с flash, `M112`/`M999`,
`M108`) работают и на Linux:

```
cd host
dotnet test TeacupHost.Core.Tests -c Debug
dotnet test TeacupHost.Core.Tests -c Release
```

Workflow **Teacup Host CI** выполняется на Windows для Debug и Release:
сначала восстанавливает зависимости и собирает решение, затем выполняет
полный набор тестов ядра. После него десять раз запускаются оба регрессионных
теста — переподключение Telnet и повторная передача команд (`Resend`).
Каждая итерация обязана пройти; это не повторные попытки, скрывающие ошибки.
Журналы `.trx` публикуются как `TeacupHost-test-results-<configuration>`
даже при ошибках. После успешных тестов публикуется приложение Windows x64.

## Проверки MSI

CI выполняет реальные операции
установки, обновления в пользовательской папке, восстановления, блокировки
понижения и удаления; дополнительно проверяет все файлы, сохранение данных
и извлечение иконки из ресурса, на который ссылается установленный ярлык.

Проверка старой версии использует те же файлы
с меньшей версией MSI: она не доказывает миграцию данных между реальными
выпусками. CI не запускает WPF, не автоматизирует интерактивный мастер и
не подтверждает работу с физическим принтером.

## Проверки сборки рабочей прошивки

Workflow **Production firmware (GCC)** собирает шесть вариантов на Ubuntu:
F401C, F401E и F411E, каждый в Release и Debug. Корневой Makefile проверяет
список исходников и ICF, таблицу векторов и IRQ, размещение функций Flash
в RAM, стек и пределы памяти, согласованность ELF/HEX/BIN. Результаты
публикуются как `teacup-<chip>-<config>`. Это проверки сборки рабочей прошивки,
а не запуск тестовой конфигурации `test/gcc` и не аппаратные испытания.
